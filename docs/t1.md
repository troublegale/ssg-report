# T1. Сравнительный анализ генераторов статических сайтов

!!! abstract "Кратко"
    Рассмотрены четыре генератора на Python и около него: **MkDocs + Material**, **Sphinx + MyST-Parser/MyST-NB**,
    **Pelican** и **Quarto** (четвёртый, на выбор). Построена взвешенная матрица из 19 критериев в трёх группах,
    часть критериев измерена (время сборки, объём результата, русская морфология поиска).
    Для задачи «публикация результатов экспериментов» оптимален **Sphinx + MyST-NB** (88,7 из 100),
    второе место — **Quarto** (73,0), третье — **MkDocs Material** (64,7). Ниже — когда этот вывод меняется.

## Объекты сравнения

| | MkDocs + Material | Sphinx + MyST | Pelican | Quarto |
|---|---|---|---|---|
| Версия в замерах | MkDocs 1.6.1, Material 9.7.7 | Sphinx 9.1.0, myst-parser 5.1.0, тема Furo | 4.12.0 | 1.10.19 (`quarto-cli` с PyPI) |
| Назначение | документация, сайты-справочники | документация, книги, научные тексты | блог, личный сайт | научные и технические публикации, ноутбуки |
| Язык реализации | Python | Python | Python | TypeScript/Deno + Pandoc (Lua-фильтры) |
| Лицензия | BSD-2 (MkDocs), MIT (Material) | BSD-2 | **AGPL-3.0** | MIT (Pandoc — GPL-2) |
| Шаблоны | Jinja2 | Jinja2 | Jinja2 | шаблоны Pandoc + EJS |

!!! warning "Состояние экосистемы MkDocs на октябрь 2026"
    При каждой сборке Material 9.7 выводит предупреждение команды разработчиков (см. раздел [Отладка](otladka.md)).
    Факты из [блога Material](https://squidfunk.github.io/mkdocs-material/blog/2026/02/18/mkdocs-2.0/):
    MkDocs 2.0 — переписанный с нуля проект **без системы плагинов**, с конфигурацией в TOML и без пути миграции;
    Material с 9.7.0 (ноябрь 2025) в режиме поддержки, критические исправления продлены до 5 мая 2027 г.,
    с 9.7.5 зависимость ограничена `mkdocs<2`; репозиторий MkDocs 1.x 2 октября 2026 г. закрыт для внешних изменений.
    Преемник от авторов Material — **Zensical** (совместим с `mkdocs.yml`, но поддерживает ещё не все плагины).
    Поэтому в проекте версии зафиксированы точно (`mkdocs==1.6.1`, `mkdocs-material==9.7.7`) через `uv.lock`.

## Методика

1. **Оценки** по шкале 0–3: 3 — есть «из коробки» и работает хорошо; 2 — через официальный или зрелый плагин/расширение;
   1 — через сторонний/устаревший плагин, ручной HTML или с существенными ограничениями; 0 — нет.
2. **Веса** (сумма 100) отражают задачу *публикации результатов экспериментов*: важнее всего корректная научная разметка
   (формулы со ссылками, исполняемый контент, библиография) и эксплуатация (стабильность проекта, простота CI,
   русский поиск, версионирование).
3. **Измерения** — на одинаковом синтетическом контенте (стенд `bench/bench.py`): N страниц, каждая с формулой,
   таблицей, листингом и сноской; медиана из 3 запусков; Windows 11, Python 3.12, Intel Core Ultra 9 285H, 32 ГБ ОЗУ.
   Холодная сборка — с удалённым каталогом вывода и кэшем; инкрементальная — изменён один файл, повторный запуск той же команды.

## Измерения

### Время сборки и объём результата

| Генератор | 30 стр.: холодная, с | 30 стр.: инкр., с | 30 стр.: объём, КБ / файлов | 150 стр.: холодная, с | 150 стр.: инкр., с | 150 стр.: объём, КБ |
|---|---:|---:|---:|---:|---:|---:|
| MkDocs Material | 1,40 | 1,11 | 3 202 / 78 | 1,93 | 2,21 | 10 392 |
| Sphinx + MyST (Furo) | 2,04 | 1,81 | 1 386 / 122 | **11,42** | 2,32 | 7 417 |
| Pelican | **1,14** | **0,99** | **473** / 54 | **1,65** | **1,59** | **3 581** |
| Quarto | 23,07 | 22,13 (2,46–2,79 при `quarto render файл.qmd`) | 1 886 / 48 | — [^q150] | — | — |

[^q150]: Quarto на 150 страницах не замерялся: при ~0,75 с на страницу холодная сборка заняла бы около 2 минут, вывод очевиден.

Наблюдения:

- **MkDocs** не имеет настоящей инкрементальной сборки: каждый запуск пересобирает всё (`mkdocs serve --dirtyreload` — только для
  предпросмотра), но делает это быстро. Объём велик из-за поискового индекса и ассетов темы (~1,5 МБ JS/CSS/шрифтов).
- **Sphinx** хранит pickle-окружение и пересобирает только изменённые документы: при 150 страницах инкрементальная сборка в 5 раз
  быстрее холодной. Холодная сборка растёт сверхлинейно из-за разрешения перекрёстных ссылок.
- **Pelican** — самый лёгкий результат: тема по умолчанию почти без JS, нет поиска и формул.
- **Quarto** запускает Pandoc на каждый документ, поэтому холодная сборка на порядок медленнее; при этом рендер одного файла
  и механизм `freeze` для исполняемых ячеек делают его рабочим инструментом для ноутбуков.

### Русскоязычный поиск

Проверено, как стеммеры, встроенные в поиск, сводят словоформы к основе (скрипт на Node.js: `lunr-languages` 1.14 — используется
MkDocs Material при `lang: ru`; `snowball-stemmers` — тот же алгоритм Snowball, что в поиске Sphinx при `language = "ru"`).

| Словоформа | Основа (lunr.ru) | Основа (Snowball, Sphinx) | Найдётся по запросу «…» |
|---|---|---|---|
| регрессия / регрессии | регресс | регресс | — |
| регрессионный | регрессион | регрессион | «регрессия» — **только за счёт префиксного поиска** (Material добавляет `*` к термину) |
| эксперимент / экспериментов | эксперимент | эксперимент | да, одна основа |
| экспериментальные | экспериментальн | экспериментальн | «эксперимент» — только префиксно |
| формула / формулы | формул | формул | да |
| измерение / измерения | измерен | измерен | да |
| развёртывание / развертывания | развёртыван / развертыван | то же | **нет**: буква «ё» не нормализуется |

Вывод по критерию: MkDocs и Sphinx дают одинаковую морфологию (Snowball), MkDocs выигрывает префиксным поиском «на лету»,
Sphinx — выдачей фрагментов с подсветкой. Quarto использует `fuse.js` (нечёткий поиск по подстроке без морфологии),
Pelican поиска не имеет (плагин `pelican-search` основан на Stork, разработка которого прекращена). Общая проблема всех — «ё»:
её нужно нормализовать в тексте или отдельным хуком.

## Обоснование весов

- **Научный контент — 40.** Результат эксперимента — это формулы, таблицы и графики со ссылками на них; без нумерации
  и перекрёстных ссылок (A2, A3 — 13 баллов) текст нельзя цитировать по частям. Исполняемый контент и библиография (A6, A7 — 12)
  отвечают за воспроизводимость и научную корректность.
- **Вёрстка — 15.** Важна, но решается темой; выход в PDF нужен для сдачи отчётов и препринтов.
- **Эксплуатация — 45.** Сайт с результатами живёт дольше эксперимента: стабильность проекта (C7) и простота CI (C8) весят больше всего,
  поиск по-русски и версии результатов (C1, C2) — следующие по важности.

## Вывод

**Оптимальный генератор для публикации результатов экспериментов — Sphinx + MyST-Parser/MyST-NB.** Он единственный закрывает
все научные критерии без ручного HTML (сквозная нумерация формул и рисунков между страницами, BibTeX, глоссарий, исполнение
ноутбуков с кэшем), даёт PDF из того же источника, лучший русский поиск и при этом является зрелым активно развиваемым проектом.

Условия, при которых вывод меняется:

1. **Основной источник — ноутбуки, нужны PDF/DOCX-версии статьи, цитирование по CSL (ГОСТ)** → **Quarto**: лучший по научной
   разметке (96,7 в группе A), `freeze` для тяжёлых вычислений. Цена — медленная сборка, внешний бинарник в CI, нет версионирования.
2. **Сайт-отчёт или документация без формульных перекрёстных ссылок и исполняемого контента, важны скорость, простота
   и внешний вид, нужны версии (`mike`)** → **MkDocs Material**. Так устроен этот сайт: отчёт по заданию не содержит
   межстраничных ссылок на формулы и ноутбуков, но использует `--strict`, хуки, переопределение шаблона, сетки и privacy-плагин.
   Ограничение — риск экосистемы: при старте нового долгоживущего проекта стоит оценивать **Zensical**.
3. **Блог с заметками о ходе исследования, без формул** → **Pelican**: самый лёгкий результат и быстрая сборка; лицензия AGPL
   касается самого генератора, а не опубликованного контента.
4. **Нужен строгий учёт версий результатов при Sphinx** → `sphinx-multiversion` редко обновляется; если версионирование критично,
   а остальное вторично, MkDocs + `mike` удобнее.

!!! note "Почему сайт сделан на MkDocs, а оптимальным признан Sphinx"
    Генератор для сайта выбран до анализа — по ходу работы, рекомендованному в задании (MkDocs), и подходит под сценарий 2.
    Анализ показал, что для *научных* публикаций с вычислениями этот выбор не оптимален; для следующей работы с ноутбуками
    рекомендуется Sphinx + MyST-NB или Quarto (см. [Вывод](vyvod.md)).

## Воспроизведение

```bash
cd bench
uv sync
uv run python bench.py                      # 30 страниц, все генераторы

python matrix.py                            # итоговые баллы и сценарии
```

Исходники стенда — в каталоге [`bench/`](https://github.com/troublegale/ssg-report/tree/main/bench) репозитория.
